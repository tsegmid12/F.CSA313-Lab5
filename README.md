## Тестийн дизайны тайлбар

Эдгээр тестийн тохиолдлуудыг эквивалент хуваалтын аргыг ашиглан боловсруулсан. Ингэснээр API-д орж болох зөв, буруу болон хязгаарын нөхцөлүүдийг төлөөлөх утгуудаар ангилсан.

Тест бүр **бие даасан** байхаар зохион байгуулагдсан. Өөрөөр хэлбэл, тухайн тестэд шаардлагатай оюутан болон хичээлийн мэдээллийг `PUT` хүсэлтээр өөрөө үүсгэсний дараа `POST /registrations` хүсэлтийг ажиллуулна.

`registrationID` нь серверийн in-memory өгөгдөлд хадгалагдаж, хүсэлт бүрийн дараа нэмэгддэг тул тодорхой тоотой тэнцүү эсэхийг шалгаагүй.

Жишээлбэл, амжилттай бүртгэлийн үед HTTP статус болон response-ийн `result` утгыг тусад нь шалгана.

```javascript
pm.test("Статус код 201 байна", function () {
    pm.response.to.have.status(201);
});

pm.test("Result нь OK байна", function () {
    const json = pm.response.json();
    pm.expect(json.result).to.eql("OK");
});
```

Энд:

* Эхний oracle нь HTTP статус `201` эсэхийг шалгана.
* Хоёр дахь oracle нь `result` утга `OK` эсэхийг шалгана.

## Newman DOWN ажиллуулалт

Энэ туршилтыг хийхийн өмнө серверийг `Ctrl+C` ашиглан унтраасан.

Дараа нь:

```bash
newman run lab05-collection.json 2>&1 | tee results/newman-down.txt
```

ажиллуулсан.

* **Алдаа:** `ECONNREFUSED`
* **Exit code:** `1`
* **Үр дүн:** DOWN

`ECONNREFUSED` нь **интерфейсийн алдаа** юм. Энэ нь Newman сервертэй холбогдож чадаагүй гэсэн үг.

Харин **oracle-ийн алдаа** гэдэг нь сервер хүсэлтэд хариу өгсөн боловч тухайн response нь хүлээгдэж байсан утгатай тохироогүй тохиолдол юм.

Иймээс:

* **Oracle error:** Сервер ажиллаж байна → response ирсэн → response буруу.
* **Interface error:** Сервертэй холбогдож чадаагүй → `ECONNREFUSED`.

# Нийтийн API-ийн тест — JSONPlaceholder

Туршсан API:

```text
https://jsonplaceholder.typicode.com/users
```

Энэ API дээр дараах **3 oracle**-ийг шалгасан.

### 1. Статусын oracle

HTTP статус `200` байх ёстой.

### 2. Өгөгдлийн төрлийн oracle

Response-ийн үндсэн өгөгдөл нь массив байх ёстой.

### 3. Утгын oracle

Массивын эхний хэрэглэгчийн нэр:

```text
Leanne Graham
```

байх ёстой.

Тестийн код:

```javascript
pm.test("Статус код 200 байна", function () {
    pm.response.to.have.status(200);
});

pm.test("Response нь массив байна", function () {
    const json = pm.response.json();
    pm.expect(json).to.be.an("array");
});

pm.test("Эхний хэрэглэгчийн нэр зөв байна", function () {
    const json = pm.response.json();
    pm.expect(json[0].name).to.eql("Leanne Graham");
});
```

Өөрийн API-тай харьцуулахад нийтийн GET API-г тестлэх нь илүү хялбар байсан. Учир нь GET хүсэлтэд зориулж `PUT` setup хийх шаардлагагүй бөгөөд серверийн төлөвийг урьдчилан бэлтгэх шаардлагагүй. Харин серверийн өгөгдөл болон төлөвийг өөрчлөх боломжгүй тул тодорхой алдааны нөхцөлүүдийг зориудаар үүсгэн тестлэхэд илүү хэцүү байсан.

# Дүгнэлт

Энэхүү лабораторийн ажлаар оюутны төлөв, хичээлийн төлөв болон урьдач нөхцөлүүдийн хоорондын хамаарлыг харгалзан API-ийн тестүүдийг боловсруулсан. Тестийн дизайны явцад хамгийн их анхаарал шаардсан хэсэг нь тест бүрийг бие даасан байлгах явдал байсан. Учир нь `POST /registrations` хүсэлт бүрийн өмнө тухайн тестэд шаардлагатай оюутан болон хичээлийн мэдээллийг `PUT` хүсэлтээр өөрөө үүсгэх шаардлагатай байсан. Эквивалент хуваалтын аргыг ашигласнаар идэвхтэй, идэвхгүй, байхгүй оюутан болон байгаа, байхгүй хичээлийн нөхцөлүүдийг системтэйгээр хамруулсан. Мөн хоосон `coursesTaken` жагсаалт болон урьдач нөхцөлгүй хичээл зэрэг хязгаарын тохиолдлуудыг тестэлсэн. Давхар алдааны нөхцөлөөр нэг хүсэлтэд хэд хэдэн буруу нөхцөл зэрэг үүсэх үед API аль алдааг түрүүлж боловсруулахыг шалгасан. Зарим хослол нь API-ийн одоогийн хэрэгжүүлэлтэд логикийн хувьд боломжгүй байсан бөгөөд жишээлбэл байхгүй оюутан нь урьдач нөхцөл хангах хичээл үзсэн байх боломжгүй. Newman ашигласнаар амжилттай тест, зориудаар үүсгэсэн алдаатай тест болон сервер унтарсан үеийн DOWN нөхцөлийг автоматжуулан шалгасан. Мөн oracle-ийн алдаа болон сервертэй холбогдож чадаагүй интерфейсийн алдааны ялгааг баталгаажуулсан. Эцэст нь Newman-ийн бодит гаралтаас assertion-ийн тоог авч README-д тусгаснаар тайлан болон бодит тестийн үр дүнг хооронд нь нийцүүлсэн. Энэхүү тестийн дизайн нь API-ийн үндсэн үйлдэл, алдааны нөхцөл болон хязгаарын тохиолдлуудыг системтэйгээр шалгахад тусалсан.
